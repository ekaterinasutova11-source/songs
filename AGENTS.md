# Songs — инструкции по работе с проектом

## Что мы делаем

Songs («Сад звука») — пространство преподавателя вокала и учеников: песни,
аудиозаписи, тексты, переводы, заметки и инструменты для занятий. Владелец
проекта — Екатерина; общаться с ней по-русски, простыми словами, объясняя
результат и ограничения без лишних технических подробностей.

Проект включает **и работающий сайт, и будущие полноценные скачиваемые,
устанавливаемые приложения для устройств**. Сайт не заменяет приложения.
PWA сама по себе не выполняет это требование. Рабочее направление — Flutter
для Android и iPhone/iPad. Отдельное приложение для Windows исключено по прямому
указанию Екатерины; Windows используется только как компьютер разработки.
Для первоначальной настройки iOS/Xcode Cloud есть согласованный доступ к Mac
знакомого. Екатерина подтвердила наличие Apple Developer Program и iPhone;
настройку Apple-инструментов попросила отложить.

## Текущее устройство проекта

На 20 октября 2026 года основной frontend, API, медиа и шрифты размещены на
Selectel. Старый адрес GitHub Pages сохранён как переход в ветке
`codex/pages-redirect`; прежние личные ссылки учеников работают через этот переход.
GitHub остаётся репозиторием исходников. Frontend — HTML/CSS/JavaScript;
сервер — Node.js/SQLite в `migration/server.mjs` и `migration/local-store.mjs`.
Материалы хранятся на сервере, выдаются с проверкой прав и поддержкой HTTP Range.
Текущие подробности и служебные пути приведены в технических документах выше.

Архивирование опубликовано: преподаватель закрывает доступ ученика, сохраняет
его материалы и может восстановить доступ по прежней ссылке. Ученики и архив
показаны отдельно. В `mobile/` создан Flutter MVP и тестовый Android APK.
Екатерина подтвердила установку и работу первой версии на Pixel 9, прислала
системную карточку плеера. Новые сборки проверять отдельно; iOS не собиралась.

## Обязательные правила изменений

- Сохранять прежние личные ссылки, ID учеников, песни, тексты, переводы,
  заметки и настройки. Менять формат хранения через совместимую миграцию.
- Архивирование — обратимое закрытие доступа, а не удаление данных.
  Преподаватель видит архивные материалы. После восстановления работает
  прежняя личная ссылка; ранее отозванные временные билеты доступа не оживают.
- Проверять права на сервере: ученик получает только разрешённые материалы;
  административные действия доступны преподавателю. Скрытая кнопка не является
  защитой доступа.
- Не использовать число учеников на момент снимка как постоянный лимит.
  Будущие группы, дуэты и ансамбли требуют отдельных прав участников.
- Selectel — рабочий источник данных. Не включать незаметный возврат к старому
  резерву и не создавать два независимых источника записи. Откат после новых
  правок требует сохранения и переноса этих правок.
- Перед изменением рабочей базы и существенным развёртыванием создавать
  согласованную резервную копию. Сохранять резервирование архивных материалов.
- Проверять опасные сценарии на отдельном временном ученике, не изменяя
  настоящих учеников ради теста. Убирать тестовые записи после проверки.
- Не публиковать ключи учеников и преподавателя, пароли, токены, приватные
  каталоги и содержимое `secrets/`. Не выводить их в чат, логи и аргументы команд.
  `secrets/` и `outputs/` исключены из Git; это не отменяет проверки содержимого.
- Не добавлять платные услуги без согласования. Зафиксированный ориентир
  инфраструктуры — до 2 000 ₽/месяц, предпочтительнее меньше. Оценка сервера
  1 715 ₽/месяц относится к панели на момент создания, а не гарантии будущей цены.
- Сохранять существующий визуальный стиль и работоспособность плеера,
  перемотки, повторов и метронома при изменениях интерфейса.

## Проверка и завершение работы

Для повторяемых задач использовать подходящий проектный навык из `.agents/skills`:
`songs-access` — права и архив; `songs-audio` — плеер; `songs-release` — порученный
выпуск и резервирование; `songs-device-app` — устанавливаемое приложение.
Подробности и определения ролей — в docs/DEVELOPMENT_SETUP.md. Наличие роли
не означает автоматический запуск: делегировать по явному запросу пользователя,
с учётом доступных инструментов и ограничений текущей сессии.

Запускать `npm test` для изменений логики и проверки, соответствующие изменению.
Для плеера проверять воспроизведение, перемотку и продолжение; для доступа —
изоляцию учеников, закрытие и восстановление доступа; для резервов — восстановление.
После публикации проверять именно опубликованную версию и прежние ссылки.
Не выдавать серверный тест за проверку интерфейса или проверку на телефоне.
Оставшиеся ограничения проверки сообщать честно.

После существенной работы обновлять PROJECT_STATE; новые требования и решения
добавлять в PROJECT_DISCUSSIONS. Отделять пожелания от выбранных решений,
а запланированное — от реализованного. Не записывать секреты в документацию.
