# Выпуск и резервирование Songs

Прочитать AGENTS.md, актуальный верх docs/PROJECT_STATE.md и разделы
migration/README.md для нужной операции. Служебные команды и пути сверять там
и в текущих скриптах, не восстанавливать их по памяти.

Уточнить фактическую цель: frontend GitHub Pages, копия frontend на Selectel,
backend songs или данные. Не публиковать всё сразу по привычке. Проверить diff
и чистоту набора файлов для выпуска; не включать secrets/ и outputs/.

Перед миграцией рабочей базы и существенным выпуском создать согласованный
backup и проверить успешность. Не считать копию на том же сервере независимой:
есть отдельная задача копирования на Windows, зависящая от включённого ПК и SSH.
Новые поля и архивные материалы должны входить в восстановимую копию.

Проверить логические изменения через npm test. При обновлении frontend учесть
кеши index и изменённых импортов. После выпуска проверить опубликованную версию,
старые ученические ссылки и затронутый сценарий. Для Pages доступен
migration/verify-publication.mjs; сначала прочитать его текущие проверки.
Для backend проверить состояние songs и HTTPS, не печатая переменные окружения.

При сбое сохранить свежие данные и определить совместимость кода и схемы.
Не переключать запись обратно на старый Яндекс после новых правок на Selectel
без переноса дельты. Не ослаблять TLS и права доступа ради успешного smoke test.
Восстановление выполнять сначала отдельно от рабочей базы, когда это возможно;
проверять целостность SQLite, хеши материалов и поведение доступа.

Записать версию, проверки и ограничения в docs/PROJECT_STATE.md. Сам навык
не даёт разрешения менять production вне порученной пользователем задачи.
